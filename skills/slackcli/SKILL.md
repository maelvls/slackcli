# slackcli

Use `slackcli` from `$PATH`. If it is missing, tell the user: it is installed from a checkout of its repository with `go install ./cmd/slackcli`.

`slackcli --help` and each subcommand's `--help` are authoritative: they document every flag and the JSON each command prints. Read the relevant help before guessing. If a capability named here is absent from the installed help, report version skew instead of guessing.

## Safety

- Read and search freely.
- Perform a write only when explicitly requested: `message send/edit/delete`, `message react`, `message scheduled cancel`, `message draft create/update/delete`, uploads (`--attach`), `channel new/invite/mark`, `user dm-open`, `later save/complete/archive/reopen/remove/remind`, `canvas create/edit`, `workflow run`. `workflow run` is not idempotent and can trigger downstream actions: read `workflow get` first.
- For a compose- or review-only request, return the proposed text without invoking Slack, or use `message draft create`: it posts nothing and leaves a draft in the user's Slack client.
- `message compose <target> [text]` hands the text to a human: it opens an editor in their browser and blocks, with no timeout, until they send or cancel. Use it only when the user asks for the editor. You cannot send from it yourself; without a browser it fails unless stderr is an interactive terminal (in safe mode it always fails: tell the user to run it themselves). Exception: when the `CI` environment variable is set it skips the editor and sends `[text]` immediately, so in CI treat it as a send.
- Safe mode (`SLACKCLI_SAFE_MODE=1` or the global `--safe-mode`) is enforced by the tool: `message send` is redirected to the compose editor (and refuses `--attach`, `--blocks`, `--schedule`, `--schedule-in`, `--reply-broadcast`, CI, and a machine where no browser can be opened). Refused in safe mode: `message edit`, `message delete`, `message scheduled cancel`, `canvas create`, `canvas edit`, `workflow run`, `channel new` and `channel invite`. Not covered by safe mode: `message react`, `message draft *`, `channel mark`, `later *` and `user dm-open`; the rule above still applies to those. Do not turn safe mode off to get a write through; tell the user.

## Workflow

1. Run the command you need: credentials are imported on the fly from Slack Desktop or a browser. Only if it reports none, run `auth import-desktop` (or `import-chrome`, `import-brave`, `import-firefox`), then `auth test`. `auth whoami` (local, redacted) lists the workspaces and the default one.
2. Prefer a Slack message URL as the target: it carries workspace, channel and timestamp. Quote it.
3. Choose the narrowest read: `message get` for one message, `message list` for a thread or channel history, `search messages|files|all` for discovery, `unreads` for what is unread, `inbox` for who is waiting on an answer (`inbox wait` to be woken up by the next one), `watch` for what arrives from now on, `message wait` for the answer to one message.
4. Bound the output with `--limit`, `--max-body-chars` (the same flag on `message get/list`, `search`, `unreads` and `later list`; 8000 by default), `--counts-only`, and `--no-download` (`message get/list` and `search`: files are listed, not downloaded, which is faster when only the text matters).
5. For a requested write, run only that mutation and check the JSON it prints.
6. Never write `slackcli … 2>&1 | jq …`: an error is plain text on stderr, so jq answers `parse error` and you learn neither the result nor the reason, nor whether a send went through. Write `slackcli … 2>err.txt | jq …`, and `cat err.txt` when the exit code is not 0 or the output is empty (in a pipeline the exit code is jq's: check `${PIPESTATUS[0]}`, or run the command first and jq after).

## Common reads

One call each. Messages carry `time` (their `ts` as a local date and time) and `author.name`, the author's full name; mentions in `content` read `@Full Name` (24-hour cache). Address people by `author.name` of the message you answer, never by a name guessed from the topic or an earlier message; if it is missing (a bare `user_id`, after a rate limit), run `user get <user_id>` first.

- What was said in a channel since a day: `message list "#name" --oldest 2026-01-30 --expand-threads` (`--latest` ends the window; `--expand-threads` adds the replies of each thread after its first message).
- One thread: `message list "<message-url>"`.
- The DM with someone: `user get <handle|email|name>` for their ID, then `message list U…`. It fails when no DM exists; nothing is opened.
- Someone whose exact handle or name you do not know: `user search <words>` (part of a name, a handle, a title) prints the candidates, best match first. `user get` only takes an exact handle, email or name, and prints one user.
- Who said what, anywhere: `search messages "<words> from:@handle in:#channel" --no-download`. Results carry `channel_name`, `time`, `author.name` and a `permalink` to pass to `message list`.
- A channel whose exact name you do not know: `channel list --name <text>` (add `--all` for channels you are not in). A known name needs no lookup: pass `#name`.
- What a channel is about: `channel info <#name|id|url>` prints its topic, purpose, member count and whether you are in it.
- What is unread: `unreads --counts-only`, then `message list` on what matters. Plain `unreads` prints up to 10 messages per conversation.
- Who is waiting on the user (read or not): `inbox` (`--since 12h`, `2d` or `2026-01-31`, from 00:00 local time; 3 days by default). Each item is a DM (`dm`, `mpim`), an unanswered @mention (`mention`) or new replies in a thread the user posted in (`thread`), with the newest message (`ts`, `author`, `text`, `permalink`) and how many came since the user's last one (`count`, `first_ts`). Pass the `permalink` to `message list` for the thread. `truncated: true` means not everything was looked at: raise `--max-conversations` or shorten `--since`.
- To be woken up when something new waits on the user (instead of running `inbox` on a timer): `inbox wait --after <after of the previous run>`, in the background. It stays connected (one WebSocket, no polling), exits as soon as a new DM, unanswered @mention or reply in a thread the user posted in arrives, and prints `inbox`'s items plus `after`, the `--after` for the next run (nothing is lost between runs: with `--after` it first searches what came since, and again after a reconnection). Without `--after` it waits from now on. The first result takes at least 15 s (a final search covers the index lag); if a search failed, `after` stays at `--after` with a warning, so an item may come twice. `--timeout 2h` ends with `items: []`, `timed_out: true`; both exit 0.
- What arrives from now on, live: `watch --for 10m` prints one JSON line per new message of every conversation you are in (thread replies included, read or not); `--channel` narrows it, `--text` prints readable lines. Without `--for` it runs until interrupted: give it a duration, or run it in the background.
- The reply to a message you just sent: `message wait '<permalink>'` (the one `message send` printed), run in the background. It prints the new messages (`list`'s shape) once someone posts after it, in its thread or at the top level of the conversation (your own messages too; those already there at once), then exits. It asks every `--interval` (1m), keeps trying while Slack cannot be reached (a closed lid, a dropped VPN: unlike `watch`, nothing is lost), and stops on any other error. No time limit unless `--timeout 2h`, which ends with `messages: []`, `timed_out: true` and a hint giving the `--after` to wait again; both exit 0. Do not write your own `message list` loop.

## Non-obvious behaviour

- Channel history (`message list <channel>`) has top-level messages only; a message with `reply_count` started a thread: list it, or pass `--expand-threads`. System messages (joins, leaves, topic changes) are left out and counted in `system_messages_hidden`; `--include-system` lists them. `--oldest`/`--latest` take a day (`2026-01-31`, from 00:00 local time), a date and time (`2026-01-31T14:30`) or a ts. Thread listings reject history-only flags (`--limit`, `--oldest`, `--latest`, `--expand-threads`, `--include-system`, reaction filters). Reaction filters require `--oldest`.
- Output is one line of JSON (indented only on a terminal). Warnings and hints are inside it, in `warnings` and `hints` (why a list is empty, what could not be fetched): read them: a command that succeeds and prints JSON writes nothing on stderr. `channel list` prints `{id, name, user, is_private, is_im, is_mpim, is_archived, num_members}`; `--raw` prints Slack's own objects, twenty times larger.
- A bot's message has `author.bot_id` and no `author.user_id`: in jq, write `.author.user_id // .author.bot_id`.
- `search` without `--channel` uses Slack's search API (operators allowed; not available to bot tokens). With `--channel` (repeatable or comma-separated) the channels are scanned and matched locally: operators are rejected, thread replies are not seen, and it can be slow: bound it with `--after`. `--after`/`--before` are exclusive days, in the Slack account's time zone (with `--channel`, the local one).
- `later`, `unreads`, `message draft` and `channel list --via-counts` need browser credentials (xoxc + cookie); `inbox` needs search, so not a bot token; `watch` needs browser credentials too, or a classic token. On an Enterprise Grid that restricts `client.counts`, `unreads` and `channel list --via-counts` read `users.counts` instead: `unreads` then has no `threads` and lists a muted conversation only when the user is mentioned in it. `canvas edit` and `canvas create --channel` need a standard token with `canvases:write`; browser credentials can only create standalone canvases.
- `message send <target> <text>` takes the text as an argument (`--text <text>` is accepted too). The text is Slack mrkdwn; lists are converted to real Slack lists. Inside them write links as `<URL|label>`: CommonMark `[label](URL)` is not converted and is posted as literal brackets. `message edit` takes the same text and keeps its links (it sends them as rich_text, since Slack leaves the links of an edited plain text unlinked). Do not verify links by reading the message back: `message get`/`list` render a real link as `[label](URL)` too, so literal `[label](URL)` text looks the same; check the text you send instead. `--blocks` replaces that conversion; with `--attach` the text is the files' plain comment. Several `--attach` flags make one message.
- Text that starts with a dash: `message send`, `edit`, `compose` and `draft create/update` take it as text when it has several words (`- item`, `-1 for me`). A single dash-word (`-1`, `--force`) is read as a flag: put it after `--`. For `message react`, write the `-1` emoji as `:-1:`.
- Scheduling: `message send --schedule` uses `chat.scheduleMessage`, which Slack documents for app tokens only; when Slack refuses it to the default browser session, nothing is sent and the error says what to do instead (e.g. `message draft create`, for the user to schedule in Slack). `message scheduled list/cancel` work with either. Prefer `--schedule` with an ISO 8601 timestamp and explicit offset. `--schedule-in` day names, and `later remind --in` day names, use the local timezone of the machine running slackcli (9:00 by default): confirm it matches the user's intent or pass a Unix timestamp.
- `message draft update --attach` adds files; it never removes any. Drafts with a scheduled time or several destinations are refused.
- Enterprise Grid: `team_is_restricted` means Slack refuses that method to a workspace session. The `message draft` commands (list and delete are the ones refused) then retry that call by themselves with the saved session of the organisation (same person, checked), so a draft you created can be listed and deleted. For another command, or when the error says no usable organisation session is saved, follow the error: `auth import-desktop`, or run the command with `--workspace <org>.enterprise.slack.com` (`auth whoami` lists what is saved).
- `canvas edit` applies one operation per call; the default `replace` without `--section-id` overwrites the whole canvas.
- `channel invite` exits non-zero on partial failure but still prints which invites went through: read the JSON before retrying.
- Commands are cut after 30 s (exit code 124; `SLACKCLI_COMMAND_TIMEOUT_MS`), except `watch`, `inbox wait`, `message wait`, `message compose` and the uploading ones (`message send --attach`, `message draft create/update`). A rate-limited call fails at once unless `SLACKCLI_RATE_LIMIT_MAX_WAIT_MS` is set. After a timeout or an interrupt (exit code 130) of a write, the change may still have gone through: check before retrying.
- A slow or timed-out command: the timeout message on stderr says where the time went (which Slack calls, rate-limit waits, keychain) and what was still running. To see it for any command, run it again with `SLACKCLI_DEBUG=1`: each call and wait is traced on stderr with its duration (`[slackcli +1.2s] api conversations.history: 800ms, HTTP 200`). Do not combine it with `2>&1 | jq`.
- How often Slack was called, by what: every request (API call attempts, downloads, uploads, `watch` connections) is a JSON line of the audit log (`audit path`; `SLACKCLI_AUDIT_LOG=off` disables it). `audit stats --since 1h` prints totals, `by_method`, `by_source` (program, looking through shells and wrappers, and command), `by_hour`, `peak_minute`, errors and rate limits; `audit tail -n 50` the last lines. Check it before running slackcli in a loop: Slack signs out sessions that call it too often.
